# MoonVape — Telegram Mini App + FastAPI/aiogram + Supabase

Схема: **Telegram → Mini App (Next.js, Vercel) → Backend (FastAPI + aiogram, Render) → Supabase → Telegram-бот**.

* Каталог, города, остатки (отдельно для München и Hannover), корзины, заказы, оплаты, возвраты, журнал склада, взаиморасчёты и очередь уведомлений — в Supabase.
* Критичные операции — атомарные RPC в PostgreSQL. Права проверяются в RPC по таблице `admins` и Telegram ID из проверенного `initData`.
* Frontend ходит только в backend. Service Role Key — только на backend. У anon-ключа доступа к заказам, пользователям, складу и корзинам нет.

> **Статус.** Код и миграции написаны, но **не запускались** против живой PostgreSQL и Telegram в этой среде. Перед приёмом заказов пройдите шаги установки и тесты ниже. Что проверено и что нет — см. `docs/REPORT.md`.

## 3. Роли
Таблица `admins` (миграция 0003):
* **Владелец** — `telegram_id = 7858672760` (ID из текущей конфигурации `OWNER_TELEGRAM_ID`). Видит все города, управляет товарами, ценами, перемещениями, передачами денег.
* **Администратор Hannover** — `telegram_id = 7050120446`, `city_id = 'hannover'`. Видит только Hannover, может подтверждать/выдавать/отменять заказы и менять остатки своего города. Не может: менять цены и товары, переводить склад между городами, фиксировать получение денег владельцем.
* **Покупатель** — всё остальное.

Добавить администратора или отключить его:
```sql
insert into admins(telegram_id, role, city_id) values (123456789, 'city_admin', 'muenchen');
update admins set is_active = false where telegram_id = 123456789;
```

Оба администратора должны один раз нажать `/start` у бота, иначе Telegram не даст боту писать им заказы.

## 6. Цены и остатки
Через админ-панель: **Товары** → товар → цена по умолчанию и цены вариантов. **Наличие** → выбрать город → изменить количество (или «Приёмка» / «Массовое»). Каждое изменение пишется в журнал с причиной и пользователем.

## 7. Поток заказа
`Новый` → `Подготовлен` → `Выдан`. Отмена возможна из `Новый` и `Подготовлен`.
* Создание заказа резервирует остаток в городе покупателя; отмена снимает резерв; выдача списывает товар.
* **Оплата отмечается при выдаче.** Выдача заказа отмечает его оплаченным на полную сумму. Отдельной кнопки оплаты нет.
* При первом входе город ставится автоматически (первый активный), меняется в каталоге («Сменить»). Вопроса о городе нет.
* Возраст: при входе в магазин подтверждение 18+ (самообъявление: Telegram возраст не передаёт). Без подтверждения каталог, корзина и заказы закрыты и на сервере.
* Город заказа берётся из профиля покупателя на сервере. Клиент не может выбрать склад.
* Уведомление о новом заказе: **город первой строкой**, затем номер, покупатель, товары, сумма, оплата, статус.

## 8. Взаиморасчёты с Hannover
«Сумма к передаче» = оплаченные заказы − возвраты покупателям − уже переданное владельцу. Закупка, неоплаченные заказы и расходы администратора в неё не входят. Владелец фиксирует получение денег кнопкой «Зафиксировать»; повторная отправка с тем же ключом не списывает дважды.

## 9. Рассылка «Оповестить о наличии»
Ручная, без автоматики при изменении остатков. Выбор: новое поступление (с момента прошлой рассылки этого города или за 7 дней), конкретные товары, категории. Сначала предпросмотр, потом подтверждение. Текст строится из товаров, которые сейчас есть в городе. Получают только пользователи, которые выбрали этот город, нажали `/start` и не отключили уведомления. Заблокировавшие бота помечаются и пропускаются. Повтор рассылки по одному городу — не чаще раза в 10 минут.

## 10. Telegram-бот и webhook
При старте backend ставит webhook на `RENDER_EXTERNAL_URL/telegram/webhook` с секретным токеном. Проверка:
```bash
curl "https://api.telegram.org/bot<BOT_TOKEN>/getWebhookInfo"
```
Очередь сообщений: сбойные отправки повторяются (до 8 попыток с нарастающей паузой), строки заказа не теряются.

## Финансы (только владелец)

Раздел «Финансы» в админке (пункт «Ещё»). Все цифры считаются в PostgreSQL из реальных данных.

* **Выручка** — строки выданных заказов. Дата признания — момент выдачи (выдача одновременно отмечает оплату).
* **Себестоимость продаж** — `order_items.unit_cost × quantity`. `unit_cost` — снимок себестоимости товара на момент создания заказа. Если в отчёте есть строки без себестоимости, раздел это показывает: прибыль по ним завышена.
* **Валовая прибыль** = выручка − себестоимость. **Чистая прибыль** = валовая − расходы (журнал).
* **Неоплаченные открытые заказы** в выручку не входят; показываются отдельной строкой.
* **Журнал** (`finance_entries`) неизменяем: записи нельзя изменить или удалить. Ошибка исправляется **сторно**: исходная запись остаётся в своём периоде, сторно уменьшает итог в периоде исправления.
* Фильтры: период (сегодня, 7 и 30 дней, месяц, произвольный; даты — по берлинскому времени), город, категория, товар. При фильтре по товару или категории расходы и чистая прибыль не считаются.
* Продажи в журнал не дублируются: они уже есть в заказах.

**Не реализовано в этой версии:** FIFO-партии и учёт закупок по партиям, перемещения между счетами, остатки по кассам с начальным сальдо, экспорт журнала в CSV/Excel. Себестоимость — текущая стоимость товара, зафиксированная в заказе, а не FIFO-партия. Подробнее — `docs/REPORT.md`, раздел «Версия 4».
